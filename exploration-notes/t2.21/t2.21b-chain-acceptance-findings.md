## 4. effective_tax_code_mappings live wiring confirmation (item 5)

Live values read from the running process (module-load path, driven by
`CLIENT_ID=sbodemosg` in `.env`):

```
cfg.source_system                 == 'sap_b1'
cfg.tax_code_mappings (declared)  == {}
cfg.effective_tax_code_mappings   == {'SO': 'SR', 'SI': 'TX'}
sap_b1_server._tax_code_mappings  == {'SO': 'SR', 'SI': 'TX'}   # module-level, live
sap_b1_server._client_config.client_id == 'sbodemosg'
```

`sbodemosg.yaml` declares no `source_system` (defaults to `"sap_b1"`) and no
`tax_code_mappings` (defaults to `{}`), so `effective_tax_code_mappings`
resolves entirely via the built-in SAP B1 default
(`config/loader.py`'s `_SAP_B1_DEFAULT_TAX_CODE_MAPPINGS`). The module-level
`sap_b1_server._tax_code_mappings`, set at import time from
`_client_config.effective_tax_code_mappings`, matches this exactly and is the
dict actually passed into every `normalize_vat_group(raw_code,
_tax_code_mappings)` call observed during this run (the raw `SO`/`SI` ->
`SR`/`TX` translation visible in the vatgroup_inventory/box results above is
the live effect of this mapping). `run_chain` separately re-confirms this by
passing `client_config.effective_tax_code_mappings` into
`sap_b1_server.configure_client(...)`, which produced the identical
`vatgroup_inventory`/`boxes` results in the PDF-render run (item 4) — i.e.
both the module-load path and the chain-configured path are wired correctly
and agree (item 5 — pass).

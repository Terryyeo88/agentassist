# T2.21b pre-step — Fixture consumption-model findings (read-only)

**Status:** Read-only tracing. No source files, configs, fixtures, or
`generate_invoices.py` were modified.

**Scope:** For the 7 fixtures in T2.20 §4 plus `generate_invoices.py`, determine
whether their `"SO"`/`"SI"` VatGroup strings are (A) raw pre-normalization input
that flows through `normalize_vat_group()` before any `F5_BOX_MAPPING` lookup, or
(B) values that test code asserts against directly as canonical codes — and from
that, derive the REAL scope of string updates T2.21b's `SO→SR`/`SI→TX` rename
requires (vs. T2.20's blanket ~472-occurrence estimate).

---

## Headline result

**Neither (A) nor (B) cleanly describes most of these fixtures.** There are
**three** distinct categories in play:

- **(A) raw passthrough** — never touches `normalize_vat_group`/`F5_BOX_MAPPING`,
  stays `"SO"`/`"SI"` forever (SAP B1 still returns these raw). **No edit, ever.**
- **(B″) stale-SSOT canonical output** — a *static snapshot* of
  `normalize_vat_group`→`F5_BOX_MAPPING` output baked into a fixture at a point
  in time. T2.21b's rename doesn't touch these fixtures directly, but it renames
  the **SSOT structures fixtures are cross-checked against** (`F5_BOX_MAPPING`,
  `_BOX_VATGROUPS` in `report/sections.py`, `_vg_category`), which makes the
  baked-in `"SO"`/`"SI"` strings *inconsistent* with the renamed SSOT and breaks
  the one test that cross-references them.
- **(B-decoupled)** — a *second, independent* `"SI"` vocabulary
  (`reasoning/sap_lines.py` / `reasoning/reg2627.py`'s "Reg 26/27 SI purchase
  lines" contract) that never calls `normalize_vat_group` and is not part of
  T2.20 §1's SSOT inventory at all. Whether T2.21b touches this is an **open
  scope question**, not a forced consequence of the F5_BOX_MAPPING rename.

### 1. Pre- or post-normalization?

**PRE-normalization** — more precisely, this is a **parallel raw fetch that
never enters the normalization path at all**. `_fetch_invoices_paginated`
(`sap_b1_server.py:488`) is the *same low-level fetch primitive* used by
`calculate_f5_return` (lines 767-768), `validate_invoice_tax_codes` (lines
1053-1054), and the detect pass (lines 1172-1174) — but those callers
**additionally** run `_classify_line(...)` and/or
`normalize_vat_group(vg, _tax_code_mappings)` / `F5_BOX_MAPPING.get(vg)` on the
fetched lines (e.g. `sap_b1_server.py:1063-1067`). `reasoning/sap_lines.py`
calls the identical raw fetch primitive but **does not** apply any of that —
it runs its own independent filter (`VatGroup != "SI"`, line 46) directly on
the raw Service Layer response.

So: `reasoning/sap_lines.py`'s `"SI"` is matched against the **raw SAP B1
`VatGroup` field**, the same raw value `normalize_vat_group` would take as its
*input* — never its output. Per T2.21a's live-recon findings, SAP B1 will
continue to return raw `VatGroup="SI"` for standard-rated purchase tax lines
regardless of the Annex E canonical-vocabulary rename (AgentAssist doesn't
control SAP-side tax code config).

### 2. Does T2.21b's `SI→TX` rename break this module?

**No.** Confirming definition-of-done branch 3 (pre-normalization):

- T2.21b's rename touches `F5_BOX_MAPPING`, `_STANDARD_VAT_GROUPS`,
  `_BOX_VATGROUPS`, `_vg_category`, `_classify_line`'s canonical-code literals,
  and `sbodemosg.yaml`'s `tax_code_mappings` — **none of these are referenced
  anywhere in the call chain above** (steps 1-7 contain zero calls to
  `normalize_vat_group`, `F5_BOX_MAPPING`, `_classify_line`, or
  `_STANDARD_VAT_GROUPS`).
- `reasoning/sap_lines.py:46`'s `!= "SI"` filter continues to match SAP B1's
  raw output exactly as before. `reasoning/sap_lines.py:54`'s hardcoded
  `"vat_group": "SI"` output label, and `reasoning/reg2627.py:277`'s
  `== "SI"` check on that label, remain internally consistent.
- The 4 reg2627 fixtures' 257 `"vat_group": "SI"` occurrences +
  `fixtures_manifest.json`'s 8 + `generate_invoices.py`'s 8 (= 273, item 3 of
  T2.20's count) model exactly this raw/pre-normalization value and require
  **zero edits for T2.21b**.

### Flag for Collin (separate from T2.21b)

`reasoning/sap_lines.py` (and `reasoning/reg2627.py`, and the entire
reg2627-fixture family) will, after T2.21b, speak a **second, currently-
undocumented "SI" vocabulary** that no longer corresponds to any
`F5_BOX_MAPPING`/canonical code — it's purely "the raw SAP B1 tax code for
standard-rated purchases," labelled with the *pre-Annex-E* name. This was
already true before T2.21b (it's a raw-SAP-code match, not a canonical-code
match), but the rename makes the naming collision/divergence more visible:
readers may assume `reasoning/sap_lines.py`'s `"SI"` means the same thing as
the old `F5_BOX_MAPPING["SI"]` canonical code, when actually after T2.21b the
canonical equivalent is `"TX"` while this module's literal stays `"SI"`
(matching SAP B1's raw output, which itself doesn't change).

Whether to (a) leave it as-is (raw-SAP-code naming, decoupled by design), (b)
rename the *label* to something raw-code-flavoured (e.g. keep matching raw
`"SI"` but rename the output `vat_group` key/value to avoid colliding with the
canonical vocabulary), or (c) migrate it to the new canonical name in a later
slice, is **a scope decision for a future task, not T2.21b**.

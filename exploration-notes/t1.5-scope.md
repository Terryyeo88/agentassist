# T1.5 Audit Trail & Input Immutability — Scope & Design

**Branch:** `t1.5-audit-trail`  
**Date:** 2026-06-02  
**Status:** Scoping / pre-implementation

---

## 1. Goal

Each chain run becomes a sealed, timestamped, tamper-evident, secrets-stripped bundle so the signed PDF report is a defensible work product. If IRAS audits a client and asks "what data did your system examine and how did it reach these findings?", the reviewer must be able to produce the bundle for that run, verify that no file has been altered since sealing, and demonstrate that the chain executed the steps it claims to have executed — without disclosing SAP credentials or any other secret that passed through the config layer. The audit bundle is the durable, self-contained evidence record that sits behind the signed report.

---

## 2. Bundle Layout

Every chain run writes its bundle under a fixed path derived from client, period, and run timestamp:

```
audit/
└── <client_id>/
    └── <period_start>_<period_end>/
        └── <run_ts>/                         # e.g. 20260601-091128
            ├── manifest.json                 # tamper-evident root; sealed last
            ├── config.json                   # allow-listed client config; no credentials
            ├── inputs/
            │   └── fetch-manifest.json       # FetchManifest from Step a
            ├── steps/
            │   ├── calculate.json            # F5ReturnOutput from Step c
            │   ├── classify.json             # ClassifyOutput from Step b
            │   └── detect.json              # DetectOutput from Step d
            ├── gates.json                    # all five gate results (see §5)
            ├── compile-output.json           # full CompileOutput from Step e
            └── report.pdf                    # signed PDF report from T1.4
```

The `<run_ts>` component is `YYYYMMDD-HHMMSS` in UTC, matching the existing
`chain-run-<ts>.json` naming convention from T1.6. The `<client_id>` and period components are
taken directly from the `ClientConfig` and `Period` objects passed into `run_chain`.

## 3. manifest.json Schema

`manifest.json` is the last file written; it covers everything else in the bundle.

```json
{
  "schema_version": "1.0",
  "engagement": {
    "client_id": "sbodemosg",
    "client_name": "SBODEMOSG Demo Company",
    "period": {"start": "2024-07-01", "end": "2024-09-30"},
    "run_ts": "20260601-091128",
    "run_started_at": "2026-06-01T09:11:17.649983+00:00",
    "run_completed_at": "2026-06-01T09:11:28.441921+00:00"
  },
  "provenance": {
    "llm_in_run_path": false,
    "model_id": null,
    "repo_commit": "a2e57b2",
    "chain_version": "t1.6",
    "report_template_version": "t1.4",
    "system_prompt_hash": "sha256:<hex>",
    "kb_slice_hash": "sha256:<hex>",
    "expected_rate": 0.07,
    "rederivation_grade": "same-SAP-state"
  },
  "artefacts": [
    {
      "path": "compile-output.json",
      "sha256": "<hex>",
      "bytes": 48291
    },
    {
      "path": "config.json",
      "sha256": "<hex>",
      "bytes": 512
    },
    {
      "path": "gates.json",
      "sha256": "<hex>",
      "bytes": 1024
    },
    {
      "path": "inputs/fetch-manifest.json",
      "sha256": "<hex>",
      "bytes": 22041
    },
    {
      "path": "report.pdf",
      "sha256": "<hex>",
      "bytes": 198312
    },
    {
      "path": "steps/calculate.json",
      "sha256": "<hex>",
      "bytes": 8192
    },
    {
      "path": "steps/classify.json",
      "sha256": "<hex>",
      "bytes": 9450
    },
    {
      "path": "steps/detect.json",
      "sha256": "<hex>",
      "bytes": 7168
    }
  ],
  "root_hash": "sha256:<hex>"
}
```

**Field notes:**

- `llm_in_run_path`: always `false` for the T1.6 chain. The chain calls the three MCP tools
  directly; no LLM inference sits on the arithmetic path. Set to `true` only if a future chain
  version reintroduces Claude invocations into steps b/c/d.
- `model_id`: `null` when `llm_in_run_path` is `false`; set to the Anthropic model ID (e.g.
  `"claude-sonnet-4-6"`) when `true`.
- `repo_commit`: short SHA of the HEAD commit at run time (`git rev-parse --short HEAD`).
  Records which version of the chain code produced this bundle.
- `chain_version`: string tag identifying the orchestration chain revision, e.g. `"t1.6"`.
- `report_template_version`: string tag for the PDF report package revision, e.g. `"t1.4"`.
- `system_prompt_hash` / `kb_slice_hash`: SHA-256 of the system prompt and knowledge base slice
  files at run time. Guards against a run being replayed with a silently different prompt.
- `expected_rate`: GST rate passed to validate and detect steps; sourced from `ClientConfig`.
- `rederivation_grade`: a human-readable assertion about replay fidelity (see §6 below).
- `artefacts`: sorted by `path` (ascending, lexicographic); all paths are relative to the
  bundle root. Each entry covers every file except `manifest.json` itself.
- `root_hash`: SHA-256 over the canonical JSON form of the manifest with the `root_hash` field
  removed (see §4).

## 4. Root-Hash Construction and Verification

### Seal (write time)

1. Build the full manifest dict with `root_hash` set to the string `"PENDING"`.
2. Remove the `root_hash` key to produce `manifest_without_root`.
3. Serialise `manifest_without_root` to canonical JSON: keys sorted recursively, no insignificant
   whitespace, UTF-8 encoding, `artefacts` array sorted by `path` ascending.
4. Compute `sha256(canonical_bytes)` — this is `root_hash`.
5. Write the final manifest with `root_hash` set to `"sha256:<hex>"`.

### Verify (read time)

1. Load `manifest.json`; extract and store `root_hash`.
2. Remove `root_hash` from the dict.
3. Re-serialise with the same canonical rules; recompute SHA-256.
4. Assert recomputed hash equals stored `root_hash` → confirms manifest is unaltered.
5. For each entry in `artefacts`: read the file at `bundle_root / entry["path"]`; compute
   SHA-256; assert equals `entry["sha256"]` → confirms each artefact is unaltered.

If any assertion fails, the bundle is tampered or corrupt. A mismatch on `root_hash` means the
manifest itself was edited. A mismatch on an artefact hash means that specific file was edited
after sealing.

## 5. gates.json Schema

`gates.json` records the result of every gate check in the chain, so the bundle documents not
just the outputs but the intermediate reconciliation decisions.

```json
{
  "all_passed": true,
  "gates": [
    {
      "gate": 1,
      "name": "record-count",
      "after_step": "fetch",
      "status": "WARN_PASS",
      "passed": true,
      "checked": {
        "sap_inline_count": null,
        "fetched_count": 73
      },
      "message": "SAP $inlinecount unavailable — cannot verify pagination completeness"
    },
    {
      "gate": 2,
      "name": "box-reconciliation",
      "after_step": "calculate",
      "status": "PASS",
      "passed": true,
      "checked": {
        "box_4_actual": 198432.10,
        "box_4_expected": 198432.10,
        "box_8_actual": 17045.87,
        "box_8_expected": 17045.87
      }
    },
    {
      "gate": 3,
      "name": "inventory-consistency",
      "after_step": "classify",
      "status": "PASS",
      "passed": true,
      "checked": {
        "summary_total": 21,
        "issues_count": 21,
        "unknown_vat_groups": []
      }
    },
    {
      "gate": 4,
      "name": "detect-consistency",
      "after_step": "detect",
      "status": "PASS",
      "passed": true,
      "checked": {
        "severity_count_sum": 21,
        "issues_count": 21,
        "dangling_doc_nums": []
      }
    },
    {
      "gate": 5,
      "name": "cross-tool-consistency",
      "after_step": "compile",
      "status": "PASS",
      "passed": true,
      "checked": {
        "calc_e1_doc_nums": [958, 960, 962, 964, 966, 968, 970, 972, 974, 976, 978],
        "detect_e1_doc_nums": [958, 960, 962, 964, 966, 968, 970, 972, 974, 976, 978],
        "e1_sets_match": true,
        "calc_unknown_vg": [],
        "classify_unknown_vg": []
      }
    }
  ]
}
```

**Field notes:**

- `status`: `"PASS"` — check ran, all assertions passed; `"WARN_PASS"` — check ran, soft warning
  issued, chain continued; `"FAIL"` — check ran, `GateFailure` raised, chain halted. A bundle
  with any `FAIL` gate is incomplete by definition (the chain did not reach seal).
- `all_passed`: `true` iff every gate has `passed: true`. Convenience field for quick triage.
- `checked`: a gate-specific dict of the values that were compared. What goes in here is
  specified per gate in the gate implementation; the schema is open — different gates record
  different fields.
- `message`: optional; present only when `status` is `WARN_PASS` or `FAIL`, carrying the
  human-readable text that was logged or raised.

## 6. Tension Resolutions

Three design tensions were identified and signed off before implementation. They are stated here
plainly so future maintainers can evaluate whether the resolution still holds.

**Tension 1 — What counts as "immutable" input?**

The chain fetches from a live SAP B1 Service Layer. The SAP data is not frozen at the moment
the chain runs; another user could alter an invoice between the chain's fetch step and a
hypothetical re-run one hour later. The bundle records the fetched payload in
`inputs/fetch-manifest.json` and hashes it. This is sufficient to prove that the chain operated
on a specific dataset; it does not prove that dataset is the only dataset that existed. The
honest claim is: *this bundle documents exactly what the chain saw at run time*. Immutability
applies to the bundle contents after sealing, not to the upstream SAP state.

**Tension 2 — Re-derivability vs. LLM non-determinism.**

The T1.6 chain is deterministic: no LLM calls sit on the arithmetic path. Re-running the chain
against the same SAP data state reproduces `compile-output.json` byte-for-byte. The
`rederivation_grade: "same-SAP-state"` field in provenance records this guarantee explicitly.
Full offline replay from frozen line bytes — where the chain runs against a snapshot rather than
a live SAP connection — is deferred to the Tier-2 source adapter. Until that adapter exists,
re-derivability requires a live SAP instance with the same data state.

**Tension 3 — Secrets exclusion vs. config completeness.**

`config.json` in the bundle must carry enough context for a reviewer to understand which SAP
instance and company database was queried, without including credentials that would allow someone
with the bundle to authenticate to that SAP instance. Resolution: `config.json` is built from an
explicit ALLOW-LIST of `ClientConfig` fields. The fields `username`, `password`, and `ssl_verify`
(which carries the PEM path or boolean, potentially exposing cert infrastructure) never enter the
bundle. All other fields — `client_id`, `client_name`, `gst_registration_number`,
`applicable_gst_rate`, `service_layer_url`, `company_db`, `fiscal_year_start_month`,
`custom_vat_groups`, `completeness_threshold`, `reviewer_name`, `firm_name` — are included.
`service_layer_url` is included because it identifies the SAP instance for audit purposes; it
carries an IP address but not authentication material. If a future client's `service_layer_url`
is itself a secret (e.g. a private endpoint), the ALLOW-LIST must be updated with client-specific
overrides.

## 7. Secrets Policy

`config.json` is written by explicitly selecting allowed fields from `ClientConfig`. The
implementation must use an ALLOW-LIST (not a DENY-LIST), so that any field added to `ClientConfig`
in the future is excluded by default until explicitly added to the allow-list.

```python
CONFIG_ALLOW_LIST = {
    "client_id", "client_name", "gst_registration_number",
    "applicable_gst_rate", "service_layer_url", "company_db",
    "fiscal_year_start_month", "custom_vat_groups",
    "completeness_threshold", "reviewer_name", "firm_name",
}
```

Fields that must never enter the bundle: `username`, `password`, `ssl_verify`.

The allow-list check must be enforced in `audit_bundle.py`, not in `config/loader.py`. The
loader's job is to resolve and validate credentials; the bundle writer's job is to strip them.
Mixing these concerns would make it possible for a loader change to accidentally propagate a
credential into a bundle.

## 8. run_agent.py Seam

The audit bundle integrates at the `run_agent.py` level, not inside `orchestrator/chain.py`.
The chain's job is to run the steps and gates and return `CompileOutput`; bundle sealing is the
caller's responsibility. The seam looks like:

```python
# run_agent.py (schematic)
from orchestrator.chain import run_chain
from report import generate_report
from audit_bundle import seal_bundle

client_config = load_client_config(args.client)
compile_output, run_ts = run_chain(client_config, period)
report_path = generate_report(compile_output, client_config)
seal_bundle(
    client_config=client_config,
    compile_output=compile_output,
    report_path=report_path,
    run_ts=run_ts,
)
```

`seal_bundle` is responsible for:
1. Creating the bundle directory tree under `audit/<client_id>/<period>/<run_ts>/`.
2. Writing each step output, the gates record, and `config.json` (allow-listed).
3. Computing per-artefact SHA-256 hashes.
4. Computing the root hash over the canonical manifest.
5. Writing `manifest.json` as the final file.

`run_chain` must return the `run_ts` it used so `seal_bundle` can write the bundle under the
same timestamp that appears inside `compile_output` and the report. This means `run_ts` becomes
a first-class return value of `run_chain` (it currently writes the chain-run JSON itself —
that write moves into `seal_bundle` in T1.5).

## 9. Test Plan

| ID | Description | Type | Pass condition |
|----|-------------|------|----------------|
| T1 | `seal_bundle` creates correct directory tree | unit | `audit/<id>/<period>/<ts>/` exists; all seven expected files present |
| T2 | `config.json` excludes credentials | unit | Loading config.json and checking keys: `username`, `password`, `ssl_verify` absent; `client_id`, `service_layer_url` present |
| T3 | Root-hash round-trip | unit | `seal_bundle` then `verify_bundle` on same dir passes with no assertion errors |
| T4 | Tamper detection — manifest field | unit | After sealing, edit one field in `manifest.json` (not `root_hash`); `verify_bundle` raises `TamperDetected` |
| T5 | Tamper detection — artefact file | unit | After sealing, append one byte to `compile-output.json`; `verify_bundle` raises `TamperDetected` |
| T6 | `gates.json` all_passed consistent with gate statuses | unit | Bundle with a WARN_PASS gate has `all_passed: true`; bundle with a FAIL gate has `all_passed: false` |
| T7 | Canonical JSON is stable across Python runs | unit | Two calls to the canonical-serialiser with the same input produce identical bytes; artefacts sorted by path; keys sorted recursively |
| T8 | Bundle directory is read-only after seal | unit | After `seal_bundle`, directory and files have read-only advisory markers set; verify behaviour is best-effort/advisory (see caveat below) |
| 124-baseline | Existing 124 tests unchanged | regression | `pytest -q` reports 124 passed, 0 failed, 0 errors before any T1.5 code is added |

**Read-only caveat (T8):** Marking bundle files read-only after sealing is best-effort and advisory. On Windows, `os.chmod(path, stat.S_IREAD)` sets the read-only attribute, but an administrator or the process owner can always remove it. The tamper evidence is the hash, not the file permission. The read-only flag is a usability guard against accidental edits; it is not a security control. Test T8 verifies that the flag is set; it does not assert that the file is unwritable, because that assertion would be platform-dependent and would fail on CI running as root.

## 10. Deferred

| Item | Reason deferred |
|---|---|
| Full offline replay from frozen SAP line bytes | Requires Tier-2 source adapter; deferred from T1.6 as well |
| Bundle encryption at rest | Key management adds complexity disproportionate to benefit at current scale; revisit at first external client |
| Bundle signing with reviewer private key | T1.4 already delivers reviewer signature block in the PDF; a separate cryptographic signing layer on the bundle is deferred until a client asks for it |
| Streaming seal (seal-as-you-go during the chain run) | Adds chain coupling; batch seal at completion is simpler and safe given current run durations (~10s) |
| Git-history scrub of pre-T1.3 credentials | See `exploration-notes/security-decisions.md`; conditions have not yet been met |

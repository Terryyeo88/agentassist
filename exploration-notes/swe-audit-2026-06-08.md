### Architectural invariants confirmed

**(a) Gates and box computation never read reasoning output.** In `run_agent.py`, `run_chain()` (line 136) returns `(compile_output, gate_results)` before `run_reg2627_pass()` is called (line 154). Box 8 is read from `compile_output["calculate"]["boxes"]` (line 169) before `reasoning_artefact` is used for anything other than status-printing. There is no data path from `reasoning_artefact` into `compile_output` or `gate_results`.

**(b) Reasoning output consumed only in report rendering, behind `show_ai_candidates`.** `reasoning_artefact` flows to `build_report(..., judgment_artefact=reasoning_artefact)` (line 208) and `seal_bundle(..., reasoning_artefact=reasoning_artefact)` (line 224). Inside `build_report()`, `show_ai = getattr(client_config, "show_ai_candidates", False)` (`report/report.py:156`); when `False`, `build_ai_candidates_section` returns `status="disabled"` immediately without reading the artefact at all (`report/sections.py:664-668`).

**(c) `llm_in_run_path` is False.** Set at `audit_bundle/provenance.py:104` — hardcoded literal `False` in `gather_provenance()`. The reasoning artefact carries its own separate `in_run_path: True` flag in `judgment-candidates.json` (stored under a distinct `llm` key in the manifest), which is never merged into the global provenance block.

## 6. Config Management

### Structure

`config/loader.py` implements `load_client_config(client_id, *, check_connectivity, config_dir) -> ClientConfig` with an 8-step validation pipeline:

1. File existence check (`config/clients/<client_id>.yaml`)
2. YAML parse (`yaml.safe_load`)
3. Required fields (`client_id`, `client_name`, `applicable_gst_rate`, `sap_b1.*`)
4. `client_id` / filename consistency check
5. Credential env-var resolution (`os.environ[username_env_var]`)
6. GST rate plausibility check (`0.05 ≤ rate ≤ 0.15`)
7. `custom_vat_groups` collision detection against `_STANDARD_VAT_GROUPS` (18 standard IRAS codes)
8. Optional SAP B1 login probe (POST `/Login`, then `/Logout`)

All failures raise `ConfigError(RuntimeError)` with human-readable messages and remediation hints. No silent defaults on critical fields.

### `ClientConfig` dataclass

Defined at `config/loader.py:76-118`. All fields are fully resolved at construction time (credential env-vars already expanded; trailing slashes stripped from URL). Treated as read-only after construction.

### `show_ai_candidates` default

```python
# config/loader.py:118
show_ai_candidates: bool = False
```

Default is `False` at the dataclass field level. The YAML loader enforces this at `config/loader.py:264`: `_raw_ai = report.get("show_ai_candidates", False)`. The value must be a Python/YAML boolean; strings are rejected with a `ConfigError`. The flag controls PDF rendering only — the reasoning pass always runs and its artefact is always sealed into the bundle.

## 7. Error Handling & Logging

### Dominant patterns

**`orchestrator/`:** Each of the five gates is wrapped in `try/except GateFailure ... raise` blocks in `chain.py` (lines 160, 178, 188, 198, 208). Gates raise `GateFailure` (defined in `orchestrator/exceptions.py`) which carries a human-readable message and an optional `checked` dict of the values that triggered the failure. `GateFailure` propagates to `run_agent.py` which catches it, prints to stderr, and calls `sys.exit(1)`. `ConfigError` follows the same pattern. Neither is swallowed.

**`reasoning/reg2627.py`:** Broad `try/except Exception` wraps each of three failure points: KB file load (line 264), `line_source()` call (line 272), LLM call per batch (line 324), and JSON/validation parse (line 348). All failures return `_errored(error_message)` — a complete artefact dict with `status="errored"` — so the pass never raises to the caller. This is by design: a reasoning failure must not block sealing. Errors are logged via `log.error(...)`.

**`mcp-servers/custom/sap_b1_server.py`:** Single automatic 401-retry: on a 401 response, `request()` calls `self.login()` and retries once (lines 183-186). No exponential backoff, no configurable retry count. Timeouts are set on individual requests via `httpx`.

**`config/loader.py`:** `requests.exceptions.ConnectionError` and `Timeout` are caught in `_probe_sap_login()` and converted to `ConfigError` with endpoint URL and remediation hint.

**`audit_bundle/`:** No try/except inside seal operations; failures propagate as bare exceptions. Bundle sealing is expected to run in a clean environment where I/O failures are fatal.

### Retry / backoff

No retry or backoff logic exists in `orchestrator/`, `reasoning/`, or `audit_bundle/`. The sole retry is the single 401 re-auth in the SAP HTTP client. A known open TODO for `reasoning/reg2627.py` reads: *"Add per-batch retry (backoff on 503/timeout)"* (`exploration-notes/t2.7-measurement/known-limitations.md:198`).

### Logging setup

`logging.getLogger(__name__)` is used in `orchestrator/gates.py`, `orchestrator/steps.py`, and `reasoning/reg2627.py`. The SAP client (`mcp-servers/custom/sap_b1_server.py`) uses `logging.basicConfig(stream=sys.stderr)` with level `INFO` and a named logger `"sap-b1-mcp"`. No structured logging (JSON) or log-level configuration file exists.
